**Understanding From Jira**
- Issue understood: A user who is an Admin User inside an AEM Guides Folder Profile (a delegated content-governance role scoped to a specific folder, not the whole AEM environment) can no longer add or remove other Admin Users on that folder profile unless they are also a member of AEM's local `administrators` group - the UI shows a success message but the change is silently not saved.
- Why it matters: Critical, customer-reported (Zebra Technologies, SLA3) regression - customers relied on delegating folder-level admin management without granting full local-administrator rights, which security/compliance teams are reluctant to grant; the loss of this capability is an operational bottleneck affecting governance of snippets, conditional attributes, templates, and output presets.
- Requested outcome: A folder-profile Admin User (a member of that profile's own admin group) must be able to add and remove other Admin Users on that same (non-global) folder profile without needing local `administrators` group membership, while the global folder profile continues to require true global-admin rights.
- Lifecycle understood as: Implementation Review - PR `starling#8091` exists; its exact diff was fetched directly from `refs/pull/8091/head` on `git.corp.adobe.com` and diffed against `origin/develop`, and the root cause is confirmed as a code refactor that accidentally dropped a permission check.
- Evidence boundary: Live Jira fetched via the backend JiraClient (Jira MCP OAuth unavailable) including all 4 comments; 3 attachments listed (2 screenshots and a screen recording of the permission behaviour) - these were not downloaded/analysed this pass because the code-level root cause and fix were already confirmed directly against the diff, and the screenshots/recording describe only the already-understood symptom (success toast with no persisted change); this is recorded as a completeness gap, not a blocker, since the fix's correctness does not depend on their content. The `C:\starling` clone was freshly fetched this pass. RAG found only general folder-profile/permission documentation with no specific coverage of this admin-delegation contract, so it is folded into Expected Behaviour as a partial-support note rather than a full grounding.

**Acceptance Criteria**
- AC-01: A user who is an Admin User on a non-global folder profile, but is not a member of AEM's local `administrators` group, can successfully add another user as an Admin User on that same folder profile, and the change is persisted (visible after a page refresh, not just a success toast).
- AC-02: The same folder-profile Admin User can successfully remove an existing Admin User from that folder profile, and the removal is persisted.
- AC-03: A user who is a member of the local `administrators` group can still add and remove Admin Users on any folder profile, exactly as before the fix - the fix must not reduce the global admin's existing capability.
- AC-04: For the global folder profile specifically, a user who is only a folder-profile Admin User (and not a true global/local administrator) still cannot add or remove Admin Users on the global profile - the fix's restored permission check must not extend to the global profile.
- AC-05: A user who is neither a folder-profile Admin User nor a local administrator cannot add or remove Admin Users on any folder profile, and receives an appropriate denial rather than a false success message.

**Expected Behaviour**
- From Jira (verified): before this regression, a folder profile's own Admin Users could manage that profile's Admin User list without local `administrators` membership; the global folder profile always required true global-admin rights, and that boundary is expected to remain unchanged by this fix.
- From product clone (verified, current code at the fetched PR): the current `develop` branch's `updateFolderProfile` method in `FolderProfilesAPI.java` gates the "update profile and users" branch on `isGlobalAdmin && !FolderProfile.GLOBAL_ID.equals(profileId)` alone - meaning only a true global admin can update Admin Users on a non-global profile today, exactly matching the reported regression (a folder-profile-only admin gets a false-success response because the branch never executes for them). The PR changes this condition to `(isGlobalAdmin || isFolderAdmin) && !FolderProfile.GLOBAL_ID.equals(profileId)`, restoring the folder-admin path while keeping the `!FolderProfile.GLOBAL_ID.equals(profileId)` guard intact so the global profile is unaffected. The separate `updateProfileConfigurations` call (folder-profile configuration settings, not the Admin Users list) already correctly allowed `isGlobalAdmin || isFolderAdmin` both before and after this fix and is not changed by the PR.
- From the ticket's own root-cause finding (verified by the PR author and confirmed independently against the diff): the missing `isFolderAdmin` disjunct was dropped during an earlier code refactor, not introduced by a deliberate security tightening - this is corroborated by the fact that the sibling `updateProfileConfigurations` gate a few lines below already uses the correct `isGlobalAdmin || isFolderAdmin` pattern, which the `updateProfileAndUsers` gate simply failed to match after the refactor.
- Unknown from current evidence: the exact commit/PR of the refactor that dropped the disjunct is referenced by the Crosshair investigation comment but was not independently verified against Starling's commit history this pass; this does not affect the correctness of the restored condition, which was verified directly against the current code.
