**Understanding From Jira**

- Issue understood: In the Map Editor, when a Global or Folder Profile's ui_config.json sets ditaAttributes.required.navtitle to true, a newly inserted <topicref> is saved without the @navtitle attribute; the expected result is that every newly added <topicref> automatically receives @navtitle populated from the referenced topic's <title> (for example <topicref href="topic1.dita" navtitle="Topic 1"/>).
- Why it matters: Customer context resolved from Jira: this is a Critical bug currently In UAC for fix version 2610 (component Editor); the documented behaviour "Include @navtitle attribute by default" promises automatic population, so authors are forced to add @navtitle by hand on every reference even though the configuration explicitly enables it.
- Requested outcome: With navtitle required in the profile, adding a topic reference to a map through the editor must auto-populate @navtitle from the referenced content's title and persist it in the saved map source, matching the documented behaviour.
- Lifecycle understood as: Pre-Development, In UAC. The Jira is Open with no linked fix or PR and no accepted UAC, so all criteria are Proposed; the current editor code was inspected in the xmleditor clone and confirms the intended mechanism and the config key, but no fix exists so it is not changed-code evidence.
- Evidence boundary: Evidence mode: degraded. Live Jira was fetched via JiraClient; the three screenshots were downloaded and analysed (the topicref Attributes panel shows only format=dita with no navtitle, confirming the actual result). The xmleditor clone was inspected and every cited path is disk-verifiable, but it was not synchronised so no SHA is claimed. Product RAG (ask_dita_expert) was not reached and search_jira_history MCP was unavailable, so grounding used the ticket's cited documentation, the inspected editor code, the OASIS DITA topicref/navtitle model, and the offline jira_qa corpus for advisory-only history.

**Expected Behaviour**

- The documented behaviour the ticket cites ("Include @navtitle attribute by default") states that when navtitle is configured as required, references added to a map automatically receive @navtitle populated from the referenced content title.
- In the OASIS DITA model, @navtitle on a <topicref> provides the navigation title; it is normally derived from the referenced topic's <title>, and @locktitle governs whether the navtitle overrides the referenced title in navigation and output.
- The inspected editor code already implements this contract: both the Insert Topic Reference dialog and the drag-and-drop path read the required-navtitle setting and, when set, write @navtitle from the fetched title if the DTD permits it (see Code Touched). The defect is that with the reporter's valid configuration the attribute is still not present on the saved topicref, so the failure is in the chain from ui_config.json ditaAttributes.required.navtitle to the applied attribute, not in the configuration shape.
- Out of scope for the fix: changing DITA validation rules, output-side rendering of navtitle (a downstream regression check only), and required-attribute behaviour for elements other than map references, unless implementation analysis proves a shared path.
