**Understanding From Jira**
- Issue understood: AEM Guides lets an administrator configure friendly (human-readable) names for XML attributes via workspace settings, but the Web Editor does not show these friendly names consistently - Full Tags View shows the raw attribute name, the Condition Attributes left panel does not show friendly names at all, and the Right Panel shows the friendly name only while selecting an attribute from its dropdown, reverting to the raw name once the attribute is applied.
- Why it matters: Major, customer-reported (TxDOT) usability issue that undermines the purpose of configuring friendly attribute names, especially for authors working with complex attribute sets, since the benefit only appears in one of several places attribute names are shown.
- Requested outcome: The configured friendly name for an attribute must be displayed everywhere an attribute name appears in the Web Editor - Full Tags View, the Condition Attributes panel, and the Right Panel both during selection and after the attribute has been applied.
- Lifecycle understood as: Implementation Review - PR `xmleditor#8069` exists and was inspected directly via `refs/pull/8069/head` on the `xmleditor` repository, diffed against `origin/develop`; the fix touches the attribute model, the condition model, the "other attributes" view model, and the editor controller.
- Evidence boundary: Live Jira fetched via the backend JiraClient (Jira MCP OAuth unavailable) including both comments; 1 screenshot attachment was not downloaded/analysed this pass since the reported symptom (friendly names inconsistent across three specific UI surfaces) is already unambiguous from the ticket's own bulleted description; recorded as a completeness gap. The `xmleditor` clone at `C:\xmleditor\xmleditor` was freshly fetched this pass. The friendly-name resolution itself is delegated to a function (`ditaTagUtil.getAttrName`/`getAttrTitle`) imported from an external dependency package (`@rh/jui-app`) whose own repository was not located or inspected this pass (no local clone, and GitHub MCP/`gh` are unavailable for the enterprise host this session) - this is recorded as an unresolved dependency-resolution gap, not assumed to work correctly.

**Acceptance Criteria**
- AC-01: In Full Tags View, an attribute that has a configured friendly name displays that friendly name instead of the raw attribute name.
- AC-02: In the Condition Attributes left panel, each conditional attribute (for example Audience, Platform, Product, Props, Other Props, Feature ID, Rev, Delivery Target) displays its configured friendly name when one exists, falling back to the existing default English label only when no workspace friendly name is configured for that attribute.
- AC-03: In the Right Panel, an attribute's friendly name is shown both while it is being selected from the attribute dropdown and after it has been applied to the element - the display must not revert to the raw attribute name once the attribute is applied.
- AC-04: An attribute that has no configured friendly name continues to display its raw attribute name in all three surfaces (Full Tags View, Condition Attributes panel, Right Panel), so the fix does not introduce a blank or broken label for unconfigured attributes.
- AC-05: When the workspace's friendly-name configuration for attributes changes (for example an administrator adds, edits, or removes a friendly name mapping) while the editor is open, the Full Tags View and Right Panel displays update to reflect the new configuration without requiring a full page reload, consistent with how friendly names for elements (not just attributes) already update live today.

**Expected Behaviour**
- From Jira (verified): the requested outcome is friendly-name consistency across exactly three named surfaces - Full Tags View, Condition Attributes panel, and Right Panel (both selection and post-apply states).
- From product clone (verified, current code at the fetched PR): a `displayName` field is added to the `Attribute` model, set from `ditaTagUtil.getAttrName(name) || name` at construction time, and the "other attributes" view model (`OtherAttributes`) now uses this same resolution for the label text shown in Full Tags View, with a `title` attribute added for the full/unabbreviated name on hover; the `Condition` model's `getGroupPath` method now resolves the friendly name the same way for the Condition Attributes panel; and the editor controller adds a live-update subscription for a `PAGE_DITA_ATTRIBUTES` app-model key (mirroring the existing `PAGE_DITA_ELEMENTS` subscription for element friendly names) that calls a new `updateTagViewAttributeFriendlyNames` command when the app model's attribute-friendly-name data changes.
