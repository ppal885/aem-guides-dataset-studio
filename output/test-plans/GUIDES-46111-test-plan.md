**Understanding From Jira**
- Issue understood: When several DITA files are uploaded in one batch and each file independently hits a UUID conflict (its GUID-style filename maps to a different existing UUID-aware asset elsewhere in the repository), Guides mishandles the batch - the conflict resolution for one file is reused or cross-applied to another file, so the wrong binary is written, moved, or renamed against the wrong existing asset; uploading the same files one at a time works correctly.
- Why it matters: Major customer-reported (Ciena) content-integrity defect - the wrong binary can silently overwrite the wrong repository asset, so authors cannot safely batch-upload GUID-named DITA files and the only workaround is uploading one file at a time, which is operationally limiting.
- Requested outcome: Each uploaded file in a batch must resolve its UUID conflict independently against its own matching existing asset, with per-file resolution state kept isolated, so batch behaviour matches single-file behaviour and no cross-over of overwrite/move/rename occurs between items.
- Lifecycle understood as: Pre-Development UAC - the issue is Open, fix version Backlog, planned for the Oct-Nov release; no fix exists yet, and a Crosshair static investigation traced candidate code paths but paused needing runtime data, so acceptance criteria are being defined ahead of development.
- Evidence boundary: Live Jira was fetched via the backend JiraClient (Jira MCP OAuth unavailable) including the full description, all 13 comments, both Crosshair investigation traces, and both attachments (a vault content-package backup of the existing assets and the three GUID DITA files to upload, both analysed as zip fixtures); RAG grounded the UUID-pattern upload/move behaviour and the duplicate.uuid.move.old.file config; the Starling clone was inspected read-only and confirms the old ImportServlet upload path but NOT the newer AssetServletV2 batch path the Crosshair trace cited (the clone predates PR 7978), which is itself a finding carried as an Open Question.

**Acceptance Criteria**
- AC-01: When multiple DITA files are uploaded in one batch and each independently hits a UUID conflict against a different existing asset, each file's conflict is resolved independently against its own matching existing asset, with no resolution state shared or cross-applied between batch items.
- AC-02: With the default Overwrite existing files resolution, each uploaded file's content overwrites only its own fmUuid-matched existing asset, and no other existing asset's content is modified.
- AC-03: A batch of N independent UUID conflicts produces the same per-file outcome as uploading the same N files one at a time, so single-file and multi-file behaviour are logically consistent.
- AC-04: No uploaded file's binary is written to the wrong repository asset, and no existing asset is renamed, moved, or overwritten as a side effect of resolving a different file in the same batch.
- AC-05: With Move old file with same UUID to new folder enabled (the product config key is duplicate.uuid.move.old.file under com.adobe.fmdita.config.ConfigManager, read into the moveOldOnDuplicateUuid flag), each conflicting existing file is moved per its own resolution and the move targets the correct existing file, not a sibling batch item's target.
- AC-06: The batch outcome is consistent across Cloud Service and SDK/on-prem for the same files and the same config, rather than the two divergent corruptions reported (Cloud: one file's content replaces both existing locations; SDK: one file left in the upload folder and renamed to an existing asset's name).
- AC-07: The conflict dialog lists each conflicting file with its own resolution, and the per-file resolution the user selects is the one applied to that specific file.
- AC-08: After the batch completes, each existing asset's binary and version history reflect only its own matching uploaded file, so content integrity is preserved with no silent wrong-asset overwrite.

**Expected Behaviour**
- From Jira (reported): batch upload of multiple independent UUID conflicts corrupts resolution - on Cloud Service one uploaded file's content replaces the content in both existing repository locations, and on SDK one uploaded file is left in the target upload folder and renamed to match an existing asset; single-file upload of the same files is correct.
- From the AEM Guides docs (verified): for a UUID-pattern filename, drag-and-drop where no same-name file exists in the destination creates a new copy with a new UUID; when the same UUID exists, the documented handling is the move/overwrite governed by the Move old file with same UUID to new folder option (duplicate.uuid.move.old.file), so the per-file expectation is a deterministic move-or-overwrite against the one matching existing asset.
- From the product clone (verified, current old path): the old drag-drop batch servlet iterates files sequentially and throws a per-file UUIDExistsException carrying that file's own otherpath, then resolves each via an OVERWRITE or MOVE operation - per-file in isolation the write targets that file's own otherpath, so the corruption most likely arises from interaction between resolution paths or shared session/stream state across iterations rather than a single obviously-wrong line.
- From the Crosshair investigation (reported, unconfirmed): three candidate resolution paths exist - the old ImportServlet resolveGuidConflict, a post-processing isConflictFoundAndResolved, and a newer AssetServletV2 batch resolveImportUuidConflict that issues an immediate workspace move visible to sibling batch items; which one fires for the customer build and whether an InputStream is reused across multipart parts could not be determined from source alone and needs runtime logs.
- Supported inference: because the reported failure only reproduces with multiple simultaneous UUID conflicts and never with single-file upload, the acceptance contract must assert per-file isolation and single-vs-multi consistency directly, and the fix must be validated against both the Cloud and SDK end-states since the same root cause surfaced as two different corruptions.
