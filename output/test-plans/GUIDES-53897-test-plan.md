**Understanding From Jira**
- Issue understood: The background cleanup job that removes leftover folder-profile "preset execution data" from DITA maps (`PurgePresetExecutionDataJob`, a Sling job on the "Guides Administrative Task Queue") pages through every `.ditamap` under `/content/dam`; when that repository query trips Oak's 100,000-node read limit and throws `RuntimeNodeTraversalException`, the job catches the error, logs it, and keeps retrying the same paging loop forever instead of stopping.
- Why it matters: On a Broadcom production author (AEM 6.51 LTS + Guides 5.1.4, same code in Cloud 2026.8.0) this caused a P1 (INC3380232) - the job wrote about 1 GB/min to error.log, filled the disk mount to 98 percent, and destabilised the author; an ongoing P2 keeps re-firing the failing job and growing logs.
- Requested outcome: The job must stop looping on the read-limit error (and on other unexpected errors), report a truthful terminal result, keep its log output measurable, and - as secondary hardening the reporter raises - honour cancellation, expose distinct progress states, and be safe to re-run; the query/index redesign and the exact defensive bound are called out as decisions still to be made.
- Lifecycle understood as: Pre-Development UAC - the ticket is Open with fix version Backlog and no pull request exists yet; these acceptance criteria are the sign-off contract for the fix to be built, with undecided design choices kept in Open Questions rather than written as acceptance criteria.
- Evidence boundary: Live Jira fetched via the backend Jira client (Atlassian MCP OAuth not available this session); current behaviour grounded by reading the handler in the Starling clone and the queue OSGi config; product behaviour grounded by AEM Cloud indexing RAG; history from live Jira JQL because the indexed `search_jira_history` tool is not exposed this session; the ticket has no file attachments, only inline log and code blocks which were read.

**Acceptance Criteria**
- AC-01: When the map-enumeration query throws the Oak read-limit error, the job issues no further page query and the invocation ends rather than continuing to run.
- AC-02: When any query, delete, or save raises an unexpected error, the invocation ends and does not re-issue the same page in a continuous loop within that execution.
- AC-03: A single job execution writes the read-limit error at most once and issues no further page query after it, and across the queue's configured retry policy the job runs at most 3 times total (1 initial run plus 2 retries) before it stops being re-queued.
- AC-04: A run that ends because of an error reports a Sling job result of failed.
- AC-05: A run stopped by cancellation or service shutdown reports a Sling job result of cancelled.
- AC-06: A run reports a Sling job result of succeeded only when it processed every page and completed the purge.
- AC-07: After a page fails, no later page is processed in that run and the run does not report a successful result.
- AC-08: When the job is cancelled or the service is shutting down, the run stops at the next page boundary rather than continuing to completion.
- AC-09: Each failure log entry includes the Sling job id, the current page position, the query parameters, and the last successfully processed map path or an explicit "none" when no page succeeded.
- AC-10: The job's reported Sling status distinguishes a running execution from a failed execution and from a completed execution.
- AC-11: Re-running or retrying the job does not remove valid preset data and does not error on already-removed data; removing preset execution data whose node is already absent is a no-op.
- AC-12: For a map whose backing folder-profile preset no longer exists, the leftover preset execution data under that map is removed, valid presets are kept, and the change is saved.
- AC-13: On a repository with no matching map assets, the job finishes on the first page and reports a Sling job result of succeeded.

**Open Questions**
- OQ-1 read-limit / index redesign scope: Should the map query be made read-limit resilient in this ticket (a selective indexed query, path-based paging, or a `damAssetLucene` index customisation), or is that a follow-up? Impact: if in scope it becomes a sign-off criterion needing index-deployment test setup; if not, the loop-termination fix ships alone and large-repository purge stays blocked.
- OQ-2 failure taxonomy: Which exceptions are retryable versus terminal, and how many in-invocation attempts (if any) are allowed before the run ends? Impact: the taxonomy decides whether AC-02 permits a bounded in-run retry or requires immediate termination, and which errors map to the failed result.
- OQ-3 defensive upper bound value: What concrete limit (max pages/offset, run duration, or number of deletions) should terminate a runaway run? Impact: without an agreed number a defensive-bound criterion is not testable, so it is deferred here rather than written as an AC.
- OQ-4 concurrent mutation and restart semantics: With content changing during a run, or a pod restart mid-run, should the job resume from a stable checkpoint or restart, and what is the deterministic skip/duplicate oracle? Impact: this determines whether a concurrency criterion can be asserted deterministically or must stay an open design decision.
- OQ-5 retry short-circuit: On a deterministically failing read-limit query, should the job short-circuit the queue's 2 configured retries instead of repeating an identical failing run? Impact: if yes, the total-attempts bound in AC-03 drops below 3 and the log volume falls further; if no, the 3-execution bound stands.
- OQ-6 full progress states: Beyond running, failed, and completed (AC-10), should the job also distinguish stalled and retrying states? Impact: if required these need their own observable oracle and reporting mechanism; if not, AC-10's three states are the contract.
- OQ-7 recovery of previously-blocked purge: Does a post-fix successful run also complete the purge that was blocked during the infinite-loop period (recover un-purged orphan data), or only prevent new loops? Impact: if recovery is expected it needs its own criterion and a stale-then-converges scenario; if not, orphan cleanup must be tracked separately.
- OQ-8 interim mitigation: Is raising On-Premise Oak query LimitReads (QueryEngineSettings via JMX) an acceptable stopgap for Broadcom while the fix ships? Impact: if yes, QA validates a config-only mitigation now; if no, the customer stays exposed to the P2 log-flood until the code fix is released.
