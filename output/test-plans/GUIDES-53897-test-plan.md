**Understanding From Jira**
- Issue understood: The background cleanup job that removes leftover folder-profile "preset execution data" from DITA maps (`PurgePresetExecutionDataJob`, a Sling job on the "Guides Administrative Task Queue") pages through every `.ditamap` under `/content/dam`; when that repository query trips Oak's 100,000-node read limit and throws `RuntimeNodeTraversalException`, the job catches the error, logs it, and keeps retrying the same paging loop forever instead of stopping.
- Why it matters: On a Broadcom production author (AEM 6.51 LTS + Guides 5.1.4, same code in Cloud 2026.8.0) this caused a P1 (INC3380232) - the job wrote about 1 GB/min to error.log, filled the disk mount to 98 percent, and destabilised the author; an ongoing P2 keeps re-firing the failing job and growing logs.
- Requested outcome: The job must stop looping on the read-limit error (and on other unexpected errors), report a truthful pass/fail result, stop flooding the logs, and - as secondary hardening the reporter raises - become resilient to the read limit and honour cancellation, bounds, and better diagnostics.
- Lifecycle understood as: Pre-Development UAC - the ticket is Open with fix version Backlog and no pull request exists yet; these acceptance criteria are the sign-off contract for the fix to be built.
- Evidence boundary: Live Jira fetched via the backend Jira client (Atlassian MCP OAuth not available this session); current behaviour grounded by reading the actual handler in the Starling clone; product behaviour grounded by AEM Cloud indexing RAG; history from live Jira JQL because the indexed `search_jira_history` tool is not exposed this session; the ticket has no file attachments, only inline log and code blocks which were read.

**Acceptance Criteria**
- AC-01: When the map-enumeration query throws the Oak read-limit error, the cleanup job stops paging and ends the run instead of continuing to run forever.
- AC-02: When any other unexpected error occurs while querying, deleting, or saving, the job ends the run rather than silently swallowing the error and retrying the same work in a continuous loop.
- AC-03: Under the read-limit failure, the number of error and warning log entries the job produces is bounded and the run ends, so the log volume and disk usage stop growing without limit.
- AC-04: A run that ends because of an error, or that did not process every page, reports a failed or aborted job result; only a run that fully completed the cleanup reports success.
- AC-05: The page position advances only after a page has been processed and its deletions saved successfully, so a page whose query, delete, or save failed is not silently skipped and left un-cleaned.
- AC-06: When the job is cancelled or the service is shutting down, the run stops cooperatively at the next page boundary rather than continuing to completion.
- AC-07: The job enforces an agreed defensive limit (a maximum page count, run duration, or number of deletions) so repository growth or an unstable query cannot produce an unbounded run even if the normal empty-result finish is never reached.
- AC-08: Each failure log entry carries enough context to trace one run - the job id, the current page position, the last map path processed, and the query parameters - so repeated failures can be tied to a single execution and progress can be judged.
- AC-09: For a map whose backing folder-profile preset no longer exists, the leftover preset execution data under that map is still removed, valid presets are kept, and the change is saved (existing cleanup behaviour is unchanged).
- AC-10: On a repository with no matching map assets, the job finishes cleanly on the first page and reports success (the existing normal-finish path still works).
- AC-11: The map lookup is made resilient to the 100,000-node read limit - through a more selective indexed query, path-based paging, or a documented index customisation - so a large asset repository does not always trip the read-limit error (in scope for this ticket pending the scope decision in Open Questions).
- AC-12: With content changing in the repository during a run, map assets are not silently skipped or processed twice because the page position drifts across separately opened sessions (in scope pending the same scope decision).

**Expected Behaviour**
- Current behaviour, read from the handler in the Starling clone: the run method uses an unbounded paging loop whose only exit is an empty query result, so any repeating query failure never reaches the exit - confirmed at `C:\starling\core\publish-listener\src\main\java\com\adobe\aem\guides\publish\job\PurgePresetExecutionDataJob.java` L56.
- The error handler catches every exception, logs one line, and then advances the page position and repeats, which is why the Oak read-limit error produces an endless retry rather than a stop - confirmed at the same file L70 and L73.
- The run method returns a success result unconditionally after the loop, so a failed or partial run is still reported as successful - confirmed at the same file L76.
- The run method never checks the Sling stop signal, so an in-flight run cannot be cancelled cooperatively - confirmed by its absence in the same file.
- The job is scheduled for the start of the next day when a preset is deleted, and is de-duplicated so only one is queued, confirmed at `C:\starling\core\utils\src\main\java\com\adobe\fmdita\presets\service\FolderProfilePresetStrategy.java` L84; the ticket's observed per-minute re-firing is therefore a runtime loop/retry symptom, not the scheduling cadence.

**Open Questions**
- OQ-1 scope of the query/index redesign: Is the read-limit hardening (selective indexed query, path-based paging, or `damAssetLucene` index customisation) in scope for this ticket or a follow-up? Impact: if in scope, AC-11 and AC-12 become sign-off criteria and need index-deployment test setup; if not, the loop-termination fix ships alone and large-repository purge stays blocked.
- OQ-2 retry policy on failure: On a failed run, should the Sling job result be terminal (no retry) or requeued per the queue retry policy? Impact: a requeue can re-trigger the same read-limit failure every cycle (the observed per-minute spam), so the retry policy decides whether the AC-03 log-bounding actually holds in production.
- OQ-3 restart/partial-run semantics: On pod restart or shutdown mid-purge, should the job resume from a stable checkpoint or restart from the beginning? Impact: restart-from-zero re-scans and can re-process or skip pages, changing the AC-05 data-integrity assertions and the expected recovery scenario.
- OQ-4 recovery of previously-blocked cleanup: Does a post-fix successful run also complete the purge that was blocked during the loop period (recover un-purged orphan data), or only prevent new loops? Impact: if recovery is expected it needs its own criterion and a stale-then-converges scenario; if not, orphan cleanup must be tracked separately.
- OQ-5 defensive-bound value: What concrete upper limit (max pages/offset, duration, or deletions) should terminate a runaway run for AC-07? Impact: without an agreed number the criterion is not testable and each environment could choose a different limit.
