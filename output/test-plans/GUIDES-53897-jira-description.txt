*Summary:* 



When the Query Builder query throws {{RuntimeNodeTraversalException}} because it exceeds the 100,000-node read limit, the exception is caught and logged, but the {{while (true)}} loop continues. The job increments the offset and retries indefinitely, generating continuous errors and log flooding instead of failing or terminating the job.



*Background:*



This cleanup operation is started as a job (topic = "com/adobe/guides/presetexecutiondata/delete") in the async queue "Guides Administrative Task Queue". It finds all of the Guides maps in the repo using this query:

{code:java}

/jcr:root/content/dam//element(*, dam:Asset)[(jcr:like(fn:name(), '%.ditamap'))] option(offset 0, limit 50)

{code}

which uses the index "damAssetLucene".



Once the thread has a result list of maps, it performs the purge cleanup.



*Problem Description:*



But if the query throws an exception (any exception), the process() method swallows it, logs the message below, and repeats query. It repeats like this forever. 



Once the job (thread) starts it runs infinitely if the query hits the query traversal limit. 



The only "break" statement for the while() loop in this method is when the query returns an empty result set. This needs to be fixed so that it breaks the loop when an "org.apache.jackrabbit.oak.query.RuntimeNodeTraversalException" is caught. It might be a good idea to break out of the loop when some other exceptions are caught; catching all exceptions and continuing like nothing is wrong is just not a good.



Other issues with this code that should be addressed:

 # Perhaps a custom index would help with this query. The OOTB index (damAssetLucene) does have a property under indexRules for "function name()", but it does not seem to be used.

 # The executor unconditionally returns a successful result after the loop exits. Partial or failed processing is not reflected in the Sling job result, allowing an incompletely processed purge to be reported as successful.

 # Pagination progress is advanced independently of successful page completion. If query execution, deletion, or persistence fails, the current page may be skipped and never retried, resulting in incomplete cleanup and silent data omission.

 # {{PurgePresetExecutionDataJob}} does not honor Sling job cancellation. The executor never checks {{{}JobExecutionContext.isStopped(){}}}, so a running invocation cannot terminate cooperatively after cancellation or administrative shutdown.

 # The job uses offset-based pagination for a large DAM query. Each page may rescan or discard an increasing number of preceding results, causing progressively higher read cost and making the query vulnerable to Oak read-limit failures. The implementation should consider keyset/path-based pagination or a more selective indexed property.

 # The job uses offset pagination across independently acquired sessions without a stable checkpoint. Concurrent repository changes can shift result positions and cause assets to be skipped or processed more than once.

 # The executor has no upper bound on execution duration, page count, or mutation count. Its termination depends solely on a successful empty query result, allowing repository growth or query instability to produce an unbounded execution.

 # The executor does not report structured Sling job progress or job-context status. Operational users cannot reliably distinguish an active, stalled, failed, or repeatedly retrying execution from queue state alone.

 # Failure logging does not include the Sling job ID, pagination offset, last processed path, or query parameters. This makes it difficult to correlate repeated failures with a specific job execution or determine whether progress is being made.
