**Understanding From Jira**
- Issue understood: In the AEM Guides web editor, clicking Insert Keyword did not open the keyword-selection dialog and instead inserted an empty `<keyword>` element - specifically when Keyword rendered as a DIRECT toolbar button rather than as an item in the overflow (more) menu. Keyword is promoted to a direct button only when the toolbar has enough width, which is reached by reducing the browser zoom (around 50%) or using a wide viewport; at normal zoom it sits in the overflow menu and worked. It reproduces when the keys are defined in the root map (or a map with more than one keymap) and the keyword is inserted from another topic.
- Why it matters: A Critical, customer-reported (Broadcom, RingCentral, Zebra) authoring defect that silently produces empty keyword references; it is a regression of a previously fixed bug (GUIDES-12950) and reproduced in both the old and new editors.
- Requested outcome: Whether Insert Keyword is invoked from the toolbar button or from the overflow (more) menu, it must behave identically - open the keyword dialog listing the keys resolved from the map (including maps with multiple keymaps and submaps) and insert a keyword that references the chosen key, never an empty keyword element.
- Lifecycle understood as: Post-Fix Validation - the fix is merged (xmleditor PR 7945, plus the 5.2.1 hotfix PR 8066), the team verified it on builds 2026.9.0.2388 and 2026.9.0.2394 including customer content, automation was added (guides-ui-tests PR 3287), and the ticket is Closed with fix versions 5.2.1 and 2609.

**Expected Behaviour**
- From Jira (verified): the acceptance behaviour is that the Keyword action opens the keyword dialog and lists keys from the map for both the toolbar button and the overflow menu; the defect was an empty keyword element inserted with no dialog.
- From RCA (verified from ticket): the Keyword toolbar item had two divergent dispatch paths - the direct button fired AUTHOR_INSERT_ELEMENT (handleInsertElement, a plain insert with no dialog) while the overflow-menu form dispatched AUTHOR_INSERT_KEYWORD (handleInsertKeyword, which shows the dialog); the fix unifies both onto the dialog dispatch.
- From product clone (verified, current code): the responsive toolbar (ResponsiveButtonKeys) promotes Keyword to a direct button only when there is enough width, and the direct-button press is routed through ResponsiveButtonKeys.AUTHOR_INSERT_ELEMENT in `editor_toolbar_controller.ts` (line 876) - this is why the bug appears only at the lower zoom / wider toolbar that turns Keyword into a direct button. `ui_config.json` wires the Insert Keyword on-click to AUTHOR_INSERT_KEYWORD (the dialog path), while the older test-data configs still show AUTHOR_INSERT_ELEMENT; handleInsertKeyword is the dialog handler.
- Supported inference: because keys must resolve across multiple keymaps and submaps, the dialog's key list must be aggregated from the whole map hierarchy, not a single keymap; confirm the aggregated list on a multi-keymap map.
