**Understanding From Jira**
- Issue understood: Avaya's Authoring and Localization teams need to hard-lock a chosen baseline once English source content is handed off for translation, and to freeze an entire publication before release, so that post-freeze edits are blocked and an audit trail records any override -- no such native feature exists in AEM Guides as of 2026.07.
- Why it matters: Without a baseline freeze, post-handoff edits reach translators causing source/target mismatch, vendor re-work, schedule delays, and additional cost; the absence of a publication-level freeze complicates release management and can invalidate regression and QA work. Avaya is an SLA3 customer on AEM Cloud Services production (cm-p181473-e1910385); a partial workaround ("Hashout" custom notification action) was provided by the Guides team but is not a permanent fix.
- Requested outcome: (1) A lock/unlock mechanism on individual baselines, available to admin and release-manager roles, that blocks edits with an inline warning and allows role-based override; (2) a publication-level freeze before release; (3) event-based email or SSE notification and a who/when/what audit trail whenever a frozen baseline or frozen publication is modified.

**Acceptance Criteria**
- AC-01 [Proposed]: (Basic) Given an admin or release-manager user has selected exactly one unlocked baseline in the Baseline panel of the Map Console | When the user invokes the lock action (lock icon or context menu option) | Then the baseline enters the locked state: a lock icon appears next to the baseline name in the list, a tooltip confirms "Baseline is locked", the Edit and Delete options are removed from the toolbar for that baseline, and only Duplicate and Unlock options remain available to admin or release-manager users.
- AC-02 [Proposed]: (Negative) Given an author-role user (not admin, not release-manager) views a locked baseline in the Baseline panel | When the author attempts to invoke Edit, Rename, or Delete against the locked baseline | Then every attempted write operation is blocked with an inline warning explaining the baseline is frozen, no changes are persisted, and the UI does not offer edit controls to the author role.
- AC-03 [Proposed]: (Negative) Given a user selects two or more baselines simultaneously where the selection contains at least one locked baseline and at least one unlocked baseline | When the user views the action toolbar | Then no lock, unlock, edit, or delete options are available in the toolbar; the mixed-state multi-selection exposes no applicable bulk actions.
- AC-04 [Proposed]: (Integration) Given a locked baseline is selected in the Translation dashboard for export to a target-language DITA map | When the export action is triggered and completes | Then the export finishes without error, a baseline object is created at the target-language DITA map path, and the newly created target baseline is in the unlocked state -- it does not inherit the source's locked status.
- AC-05 [Proposed]: (Integration) Given a locked baseline is selected as the version reference in an output preset (for example PDF, HTML5, or AEM Sites) | When output generation is triggered using that locked baseline | Then generation completes without error and the produced output reflects the topic versions pinned by the locked baseline.
- AC-06 [Proposed]: (Basic) Given a frozen baseline exists and a notification recipient list or channel is configured | When an authorized user modifies the frozen baseline (for example by unlocking and saving changes) | Then an event-based notification (email or SSE, depending on the configured channel) is sent to the configured recipients identifying the frozen baseline that was changed and the user who made the change.
- AC-07 [Proposed]: (Basic) Given any lock, unlock, or write action is performed on a frozen baseline by any user | When the action completes | Then an audit trail entry is created and retrievable, recording: the user identity (who), the timestamp (when), the baseline name, and the action type and previous or new state (what was changed).

**Regression Areas**
- Baseline list response regression is the highest-priority risk: adding a locked-state field to `BaselineListItemDto` must use a backward-compatible default (for example `false` when absent) so existing API consumers and older UI versions receive a valid response; validate with `StaticBaselineCreationIT.java` and `GetAndUpdateBaselineObjectIT.java` after the feature is built.
- Translation export path is the highest-impact integration regression: the locked flag must NOT propagate to the target baseline after export -- any propagation would silently freeze all translated baselines and block translator edits; re-run `exportBaselineIT.java` against a locked source baseline after the feature is implemented.
- Baseline duplication path in `BaselineDuplicationIT.java` must continue to work correctly on locked and unlocked source baselines; the locked-state guard added to `BaselineObjectController` or `BlService` must explicitly carve out the duplicate operation to avoid blocking it.
- Output preset baseline selection for PDF, HTML5, and AEM Sites presets must continue to work when a locked baseline is the selected version reference; publishing must not treat the locked state as a write-blocked error condition; re-run publishing IT tests with a locked baseline as the version reference.
- Dynamic baseline creation and update path in `DynamicBaselineCreationIT.java` shares `BlService` and `BlRepositoryJcr.java` with the static baseline path; any locked-state enforcement introduced in the shared service layer could affect dynamic baseline saves if the guard does not differentiate locked state from the baseline type.
- Optimistic concurrency via the existing `lockVersion` field in `BaselineV2.java` must not be confused with or interfere with the new freeze flag; a concurrent save by two admin users on a locked baseline (race to unlock-then-edit) is a concurrency risk in the shared JCR repository layer; verify the two mechanisms do not conflict.

**Open Questions**
- Publication-level freeze design: The Jira requests the ability to freeze an entire publication before release, but does not define whether this means freezing the output preset configuration, the baseline-plus-preset combination, the generated output artifact, or something else. QA impact: if it means freezing the preset configuration, AC scenarios must test the preset-save API and block re-configuration; if it means the output artifact, scenarios must validate that re-publishing or re-generating over a frozen output is blocked; without a design decision, no acceptance criterion can be authored for this capability.
- Release-manager role definition: GUIDES-5460 notes "Release-managers -- a new license should be added in the system." Has this role been defined in the AEM Groups/Permissions model, or will it map to an existing group? QA impact: if it is a new AEM group, the IT test setup in `BaselineLockIT.java` and any UI test fixtures in `guides-ui-tests` must provision that group and assign it to a test user before any AC-01 or AC-07 scenario can run; if it maps to an existing group such as `dxml-reviewers`, existing user fixtures can be reused.
- Lock/unlock API contract: Will lock and unlock be new REST endpoints (for example a new `BaselineLockController` at a new servlet path) or extensions to the existing `/bin/dxml/baseline` POST with an operation parameter? QA impact: the request schema, HTTP method, endpoint path, and response contract determine the implementation of `LockBaselineRepository` and all API-layer test assertions for AC-01 and AC-02.
- Locked-state enforcement model in AEM Cloud: In AEM as a Cloud Service, multiple author pods share the JCR. Is the locked-state check performed synchronously at the JCR layer (safe across pods) or in a single pod's service layer in memory? QA impact: if the enforcement is only at the service layer, concurrent writes from two pods could bypass the lock; the IT test for AC-02 should include a concurrent two-client POST scenario if the enforcement is JCR-based.
- Version purge interaction: If a topic version pinned by a locked baseline is later purged by AEM's version purge policy, publishing using that locked baseline may fail with a file-not-found error. Will version purging be blocked for versions referenced by a locked baseline, or will the freeze guarantee only the baseline metadata while allowing the referenced content to be purged? QA impact: if purging is blocked, a test scenario must verify that a version-purge job skips pinned versions; if not blocked, the error contract for "publish from locked baseline after version purge" must be defined and included in AC-05.
- Notification channel configuration: Is the notification channel (email or SSE) configured globally in OSGi or per-baseline? What is the default behavior when no recipient is configured -- silent fail or a logged error? QA impact: the AC-06 test requires a provisioned notification channel; if the config is OSGi-global, the IT environment must be provisioned with a mail trap or SSE listener; if per-baseline, the lock API must accept a recipient list and the request DTO must be extended, changing the IT test setup for AC-01 as well.
