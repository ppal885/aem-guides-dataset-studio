**Understanding From Jira**
- Issue understood: When a topic is added to a DITA map, two properties on the topic (`guidesParentMaps` and `guidesDirectParentMaps` - lists of GUIDs of maps that reference the topic) are updated to include that map's GUID, but when the map itself is later deleted, its GUID is never removed from those properties on the topics that referenced it - the cleanup only ever appends, never removes.
- Why it matters: Critical, customer-reported (EY, Workday) platform-stability issue with two concrete effects - a JCR performance warning for "large multi valued property" with over a thousand stale values on a single topic, and a functional bug where Map Console's Topic List report shows orphaned, title-less parent-map references (a comma with nothing after it) for maps that no longer exist.
- Requested outcome: When a map is deleted, its GUID must be removed from `guidesParentMaps` and `guidesDirectParentMaps` on every topic that had referenced it, so the properties stay accurate and Map Console reports stop showing orphaned references.
- Lifecycle understood as: Implementation Review - PR `starling#8087` exists and was inspected directly via `refs/pull/8087/head` diffed against `origin/develop`; the PR author (Ajay Sherawat) has already posted a written gap list on this Jira, and this plan independently re-verified each of his three named gaps directly against the current PR code rather than repeating his comment at face value, per this session's standing rule that a reporter's or reviewer's premise must be checked against the actual code before it is treated as current fact.
- Evidence boundary: Live Jira fetched via the backend JiraClient (Jira MCP OAuth unavailable) including all 4 comments and the audit-log attachment's filename (the `.jsonl` audit log and the reproduction screenshot were not downloaded/analysed this pass - recorded as a completeness gap, not a blocker, since the code-level fix and its gaps were independently confirmed against the diff). **Acceptance Criteria**
- AC-01: When a map is deleted (in JCR/on-premise mode, not database mode), the deleted map's GUID is removed from the `guidesParentMaps` and `guidesDirectParentMaps` properties on every topic that referenced it, so those properties no longer list the deleted map.
- AC-02: After a map's referenced topics have their parent-map properties cleaned up following that map's deletion, the Map Console Topic List report for any other map that still references the same topics no longer shows an orphaned (title-less, comma-only) entry for the deleted map.
- AC-03: When the repository is running in database mode, no cleanup job runs from this new component when a map is deleted, and the properties on referring topics continue to be managed solely by the existing database-mode cleanup flow with no duplicated work.
- AC-04: When the config property that disables Guides parent-maps processing (`disable.guidesparentmaps.processing`) is enabled, no cleanup job runs from this new component for a deleted map, consistent with how that config already disables the append-side processing.

**Expected Behaviour**
- From Jira (verified): the customer's own reproduction steps (add two topics to two maps, delete one map, observe the topics still list the deleted map's GUID and Map Console shows an orphaned entry) define the exact bug and the exact fix contract.
- From product clone (verified, current code at the fetched PR): a new JCR-observation-based `MapDeleteParentMapsCleanupHandler` and Sling job consumer `MapDeleteParentMapsCleanupJobConsumer` were added; the handler registers a listener for `NODE_REMOVED`, `PROPERTY_ADDED`, and `PROPERTY_CHANGED` events scoped to `dam:Asset`/`dam:AssetContent` nodes under `/content/dam`, maintains a bounded (10,000-entry, LRU-evicting) in-memory map from a node's JCR identifier to its Guides-specific `fmUuid` (populated lazily whenever a ditamap/bookmap's `fmUuid` property is written), and on `NODE_REMOVED` for a ditamap/bookmap looks up the deleted node's cached `fmUuid` and enqueues a cleanup job with it; the job consumer then removes that `fmUuid` from the two properties on referring topics.
- From product clone (verified, current code confirms this gap is RESOLVED, contradicting a stale review comment): the PR author's comment states "neither class checks `DatabaseConf.isDbEnabled()`", but the currently fetched PR code shows this check IS present in three places - the handler's `activate()` method (skips listener registration entirely in DB mode), the handler's `onEvent()` method (returns immediately in DB mode as a second safeguard), and the job consumer (checked at its own entry point) - so this specific named gap has already been addressed in a later revision of the same PR branch and should not be treated as still open.
- From product clone (verified, current code confirms these gaps ARE still present): (1) the in-memory cache is populated only lazily from property-write events with no bootstrap scan of existing repository content on pod startup, so a map deleted before its `fmUuid` has ever been cached (either right after a pod restart, or immediately after the map's `fmUuid` property was first written) has no cached identifier to look up, and `handleNodeRemoved` explicitly logs a warning and skips cleanup in that case - this is the exact "create-then-delete race" and "full re-bootstrap scan" gap the author described, and it remains unaddressed; (2) the listener still broadly observes `PROPERTY_ADDED`/`PROPERTY_CHANGED` across all of `/content/dam` (filtered in-process to the two node types), which is the observation-overhead gap the author also described and which likewise remains unaddressed; (3) the class Javadoc itself states this in-memory-cache approach is "an interim shim" that a future "pre-delete capture" mechanism is expected to supersede, corroborating that these two gaps are known and intentionally deferred rather than accidental.
- Unknown from current evidence: whether the separate B-tree purge helpers referenced in the Crosshair "Known gap" note (for a UUID-profile B-tree cache used in some deployment flavor) are implemented anywhere else in the codebase outside this PR's diff; this plan does not claim they exist or do not exist beyond the two files this PR touches.

**Open Questions**
