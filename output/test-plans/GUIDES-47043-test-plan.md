**Understanding From Jira**
- Issue understood: In the AEM Assets Admin UI (Author), the DITA-specific action buttons (View source, Edit topic(s), Preview map, Share UUID link) show up on the wrong assets - they appear on non-DITA files such as PNG images and PDFs, and are missing on genuine DITA files (`.dita`, `.ditamap`) where authors actually need them. The Share UUID link button also produces a broken link (a URL with an empty `uuid=` value) when the asset has no GUID.
- Why it matters: A Critical, customer-reported (SLA3, customer cm-p63456) defect that clutters the Assets Admin UI for non-Guides teams and hides the controls DITA authors need on their own files; confirmed reproducible in the customer's stage environment and by their TAM in production.
- Requested outcome: The DITA-specific buttons must show only on assets DITA authors can actually edit (`.dita`, `.ditamap`, etc.), stay hidden on non-DITA assets (images, PDFs, PPTX, etc.), and the Share UUID link button must only appear (or must be disabled) when the asset actually has a GUID - never producing an empty-UUID link. A related cosmetic font-fallback issue in preview is out of scope for this plan (no code evidence gathered for it).
- Lifecycle understood as: Implementation Review - Jira records a fix PR (`starling#8095`) with a stated root cause and a code-review comment already flagging that the fix's new render condition checks the wrong UUID property, so the acceptance contract must account for a fix that exists but is not yet correct.
- Evidence boundary: Evidence mode: degraded. Live Jira issue and all 7 comments fetched via the backend Jira client (Jira MCP OAuth unavailable this session); both attachments downloaded and visually inspected - one shows the button menu on a non-DITA PNG, the other on a non-DITA PDF, both confirming the reported symptom. The Starling clone (`C:\starling`, branch develop) was inspected read-only for the current (pre-fix) button-visibility code, the Share UUID click handler, and the URL-resolving servlet. PR `#8095` itself - the new render condition and its property fix - is not present in the local clone and GitHub MCP is not connected this session, so that diff could not be inspected; any claim about the fix's correctness stays Proposed. **Expected Behaviour**
- From Jira (verified): the correct behaviour is that DITA-editing buttons appear only for `.dita`/`.ditamap` assets and Share UUID link appears only when a GUID exists; the incorrect current behaviour is the reverse for the DITA-editing buttons and an ungated Share UUID link.
- From product clone (verified, current code): in the single-asset details/Quick-View path, `alltopics` and `allDitamaps` are initialized `true` and are only recomputed from the actual asset extension inside a loop that runs only when a grid multi-selection exists (`selections.length !== 0`); in the details view that loop never runs, so `View source`/`Preview map` default to visible regardless of asset type. `Edit topic(s)` visibility is set only inside that same loop, so it is never explicitly turned on for a DITA asset opened directly - matching the reported "missing on DITA files" symptom.
- From product clone (verified, current code): the Share UUID link click handler (`uuid-resolver.js#getUuid`) builds the `/bin/fmdita/urlresolver` URL with the resolved UUID and copies it to the clipboard with no check that a UUID was actually resolved, confirming the reported empty-UUID URL is currently unguarded.
- From product clone (verified, current code): `UuidURLServlet.doGet` logs a 432 error when the `uuid` request parameter is absent but does not return afterward, so it proceeds to resolve a null/blank UUID - a related defect independent of the button-visibility symptom.
- Refinement of developer root cause (flagged as Open Question, not silently substituted): the Jira fix-ready comment describes the cause as "inverted asset-type discrimination"; the code instead shows an uninitialized-default-plus-unset-DOM-state bug specific to the single-asset (non-grid) rendering path. The observable symptom matches; the precise mechanism is narrower. This needs the PR author's confirmation once the PR diff is reviewable.

- The reported preview font fallback to Times New Roman is Unknown from current evidence - no code path for font loading was inspected for this plan.
