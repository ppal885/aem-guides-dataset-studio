**Understanding From Jira**
- Issue understood: When an image already referenced in a topic is overwritten in the DAM (same filename, new version), the editor and an un-baselined PDF publish both show the updated image correctly, but publishing the same map through a baseline still shows the previous (stale) image version - only a manual "Reprocess Assets" plus re-saving the baseline with "latest version" selected fixes it.
- Why it matters: Critical, customer-reported (Zebra Technologies) trust and efficiency issue - authors cannot rely on baseline-based publishing for translation/regulatory reviews without manually reprocessing every changed image, and a single guide can contain 500+ images, adding hours of manual work per release with a real risk of the wrong graphic reaching translators or end customers.
- Requested outcome: A baseline entry created with the "Latest" version selector must always resolve to the asset's current version at publish time, so overwriting a referenced image is reflected in the next baseline-based publish without any manual reprocess-and-resave step.
- Lifecycle understood as: Implementation Review - two related PRs exist on this ticket's timeline: `starling#8098` (an earlier, narrower fix touching only the V2 baseline resolution strategy) and `starling#8135` (a later, broader fix touching both the V1 and V2 baseline resolution strategies, referenced by the most recent Jira comment as "Fix Ready" and flagged "Needs Human Review"); this plan is grounded on `#8135` as the current candidate fix since it is both the most recent and the more complete of the two, with `#8098`'s narrower scope explicitly noted as a superseded intermediate step.

**Acceptance Criteria**
- AC-01: For a V2 (current-format) baseline entry created with the "Latest" version selector, when the referenced image asset is overwritten (same filename, new binary version) after the baseline entry was created, publishing the map through that baseline uses the image's current version at publish time, not the version that existed when the baseline entry was created.
- AC-02: For a V1 (legacy-format) baseline entry created with the "Latest" version selector, the same current-version-at-publish-time behaviour applies - overwriting a referenced image after the baseline was created is reflected in the next baseline-based publish without a manual reprocess-and-resave step.
- AC-03: When a legacy V1 baseline (with a "Latest"-selector entry) is migrated/converted to the V2 format, the entry's "Latest" marker is preserved through the migration, so the current-version-at-publish-time behaviour continues to apply after migration rather than silently reverting to a frozen version.
- AC-04: A baseline entry created with a specific (non-"Latest") version selector continues to resolve to exactly that pinned version at publish time, even if the referenced asset is later overwritten - the fix must not cause a pinned-version baseline entry to start floating to the latest version.
- AC-05: When the "Latest"-selector re-resolution cannot determine a current version at publish time (for example the referenced asset's version history is unavailable or empty), the baseline falls back to the previously stored/persisted version rather than failing the publish or producing a null/empty version reference.

**Expected Behaviour**
- From Jira (verified): the customer's own reproduction (override a referenced image, confirm the baseline still shows the image as "latest version" in the Map Console UI, publish via that baseline, observe the PDF still contains the old image) defines the exact bug and the exact fix contract; the attached with-baseline and without-baseline PDF samples are cited by the reporter as demonstrating the discrepancy but were not independently opened this pass.
- From product clone (verified, current code at the fetched `#8135` PR): both `BaselineV1ResolutionStrategy` and `BaselineV2ResolutionStrategy` now check, for each baseline reference, whether it was created with the "Latest" selector (a new `isLatest` marker persisted on the reference/version-selector objects); if so, at traversal/publish time they look up the referenced asset's current JCR base version (falling back to scanning the full version history, excluding the root version, for the most recently created version if no base version is set) and re-resolve the reference to that current version instead of using the version value that was stored when the baseline entry was created. If no current version can be determined, both strategies explicitly fall back to the originally persisted/stored version rather than failing.
- From product clone (verified, current code confirms migration path is handled): `BaselineReferenceConverter` (the V1-to-V2 baseline migration utility) was also changed in `#8135` to copy the "Latest" marker (`newRef.setLatest(oldRef.isLatest())`) onto the converted V2 reference, so a legacy baseline entry created as "Latest" retains that behaviour after being migrated to the newer baseline format - without this line, a migrated baseline would silently lose the never-go-stale contract this fix establishes.
- Scope evolution (verified by comparing both PRs' diffs directly): the earlier PR `#8098` fixed only `BaselineV2ResolutionStrategy` (V2-format baselines only), matching the Crosshair "Merge in order, Step 1" comment describing a coordinated multi-PR fix; the later `#8135` independently re-implements the V2 fix (with a restructured helper method and a different call site inside `addBaselineRefs`) AND adds the missing V1-format fix AND the migration-marker fix - so `#8135` is not simply "`#8098` plus more," it supersedes `#8098`'s V2 implementation with a revised one.
