**Understanding From Jira**
- Issue understood: When two authors open the same DITA topic, a second author who took the edit lock without reloading can save (including Save as new version) and silently overwrite a newer version created by the first author - Guides does not validate at lock-time or save-time that a newer version exists, so the first author's work is lost with no conflict or merge warning.
- Why it matters: Critical, IBM-reported production data loss in active authoring cycles; the overwrite is silent so it is discovered late and forces manual author coordination.
- Requested outcome: On taking the edit lock (in explicit-lock mode) the editor must refresh to the latest persisted content before editing, so the second author edits on top of the current version and cannot silently overwrite newer changes on save; the version indicator must reflect the current version and the refresh must not lose the author's place in the document.
- Lifecycle understood as: Post-Fix Validation (UAT) - the UI refresh-on-lock fix is in UAT with automation (guides-ui-tests PR 3824) and a sub-task for checkout refresh (GUIDES-54810), but there is an open scope dispute about non-UI/API write paths that is not yet resolved.
- Evidence boundary: Evidence mode: degraded. Live Jira, the Acceptance Criteria field (UAC Points Discussed), all 12 comments, and the sub-task were fetched; product RAG returned only generic web-editor docs (not concurrency behaviour) and was not used for Expected Behaviour; the Starling clone was inspected for the write paths (AssetServiceImpl / referencelistener postdita). The fix diff itself was not opened this pass; the plan rests on the agreed UAC, the comment thread, and code inspection.

**Acceptance Criteria**
- AC-01: In explicit-lock mode (the "Disable edit without checkout" configuration enabled), when the second author takes the edit lock on a topic that another author updated in the meantime, the editor automatically refreshes to the latest persisted content at the moment the lock is acquired, before the second author starts editing.
- AC-02: When the editor refreshes content - on lock acquisition, on reverting live changes, or on reflecting a recently modified state - it preserves the author's current scroll position and cursor location instead of resetting to the top of the document.
- AC-03: On checkout, the topic's metadata and version indicator refresh to reflect the current persisted version, so the author sees the true current version rather than a stale one.
- AC-04: A second author who saves (including Save as new version) after taking the lock in explicit-lock mode does not silently overwrite a newer version created in the meantime through the UI editor path - the lost-update no longer occurs silently for that path.
- AC-05: The refresh-on-lock protection applies only in explicit-lock mode, because that is the only mode with a discrete lock-acquisition event to trigger the refresh; the plan states this boundary rather than assuming the protection also covers implicit edit-without-checkout mode.

**Expected Behaviour**
- From Jira/UAC (agreed): refresh-on-lock in explicit-lock mode is the accepted contract; the version indicator refreshes on checkout; the refresh preserves scroll/cursor.
- From the comment thread (verified, disputed): refresh-on-lock is UI-only. A newer version committed through a non-UI write path (the referencelistener postdita API, or an admin force-unlock) while a stale editor is open can still be silently overwritten by a Save-as-new-version, because there is no server-side version check on the save endpoint. One reviewer treats this as a system limitation; another asks for server-side optimistic concurrency (baseVersion/ETag returning 409). This is unresolved and is carried as an Open Question, not an accepted contract.
- From product clone (verified, provisional): the topic write path is reachable both from the editor and from `referencelistener` postdita / the asset service (`AssetServiceImpl`), so a UI-only refresh does not gate the API write path - consistent with the reported non-UI overwrite.
- Supported inference: a modified-timestamp check at lock-time (proposed in comments) detects intervening changes for the UI path; it does not by itself protect the API path without a server-side conflict response.

**Open Questions**
- OQ-1: Is server-side optimistic concurrency (baseVersion/ETag returning 409) on the save endpoint in scope for this Jira, or is the non-UI/API overwrite path a separate ticket or an accepted limitation? QA impact: one reviewer calls it a limitation and another asks for the 409; if in scope, an API-path concurrency AC and a 409 test are required and the fix is only partial until then; if out of scope, the plan must state that the UI fix does not close the API lost-update path, rather than signing the Jira off as fully solved.
- OQ-2: When a topic is locked and "Disable edit without checkout" is configured, should a non-UI API write (referencelistener postdita) be refused with an error, and when the topic is not locked should the API fetch the latest content before writing? QA impact: this determines the API-path acceptance criteria and whether the API must participate in the same lock/version contract as the UI.
- OQ-3: After a lock-time refresh, does the second author see a correct version number and dirty-state marker, or a confusing version bump (raised as a still-open observation in review)? QA impact: if the indicator can mislead, a version-indicator-correctness scenario is required beyond AC-03.
- OQ-4: Does the modified-timestamp-at-lock approach reliably detect all intervening changes (including non-UI ones), or only UI edits? QA impact: if it only detects UI edits, it does not address the API path and OQ-1 becomes mandatory scope.
