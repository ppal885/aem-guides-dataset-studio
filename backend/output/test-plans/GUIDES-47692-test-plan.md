**Understanding From Jira**
- Issue understood: When a DITA map is deleted from the AEM DAM repository, the `guidesParentMaps` and `guidesDirectParentMaps` multi-value JCR properties on all topics previously referenced by that map are not cleaned up -- the deleted map's GUID persists indefinitely on those topic `jcr:content` metadata paths.
- Why it matters: Two direct customer impacts for EY and Workday: (1) Performance -- AEM error.log emits "large multi value property" warnings because stale GUIDs accumulate without bound across the lifecycle of a content repository; (2) Functional -- Map Console > Reports > Topic List shows orphan entries in the Parent Map column (a comma with no title or link) because the deleted map GUID no longer resolves to an asset.
- Requested outcome: After a map is deleted, all `guidesParentMaps` and `guidesDirectParentMaps` entries referencing that map's GUID must be removed from every topic that was referred to by the deleted map; Map Console reports must show no orphan Parent Map entries for shared topics; and the "large multi value property" log warning must not appear for cleaned-up topics.

**Acceptance Criteria**

- AC-02 [Proposed]: (Basic) Given the same topology after MapTemp deletion | When the user navigates to MapRetain > Map Console > Reports > Topic List | Then the Parent Map column for the previously shared topics must display only MapRetain's title as a valid clickable link -- no blank cell, no comma-only cell, no unresolved GUID string.
- AC-03 [Proposed]: (Negative) Given a map delete where a JCR property write fails on one referenced topic mid-cleanup | When the delete completes | Then the operation must either atomically complete cleanup for all topics or fully roll back; no topic must remain in a partial state where some parent map GUIDs are removed and others are not, and an actionable error must be logged identifying the failed topic path.
- AC-04 [Proposed]: (Negative) Given a topic referenced by three maps (MapA, MapB, MapC) | When MapA alone is deleted | Then `guidesParentMaps` on the topic retains MapB's and MapC's GUIDs and does not retain MapA's GUID; Map Console reports for MapB and MapC correctly list only their own entries.
- AC-05 [Proposed]: (Integration) Given the OSGi config `disable.guidesparentmaps.processing=true` disabling parent-map indexing | When any map is deleted | Then no cleanup of `guidesParentMaps` or `guidesDirectParentMaps` is attempted; the properties remain unchanged and no error is thrown.
- AC-06 [Proposed]: (Integration) Given topics whose `guidesParentMaps` was inflated with stale GUIDs before this fix | When a save post-processing cycle runs on those topics after the fix is applied | Then no "large multi value property" WARNING appears in error.log for those topics.
- AC-07 [Proposed]: (Integration) Given a map is deleted while one of its referenced topics also has a translation copy under the repository | When the delete and cleanup run | Then the translation copy's `jcr:content` is not affected; `TranslationUtils.removeParentMapsFields()` still fires only during translation copy creation and is not double-triggered or suppressed by the new delete cleanup path.

**Expected Behaviour**
- When a map asset is deleted, Guides must traverse the `fmditaTopicrefs` multi-value property on the deleted map's `jcr:content` to collect referenced topic GUIDs, resolve each GUID to a DAM path, and remove the deleted map's GUID from `guidesParentMaps` and `guidesDirectParentMaps` on each resolved topic's `jcr:content`.
- `guidesParentMaps` on a topic must at all times reflect only GUIDs of maps that currently exist in the repository and reference that topic.
- Map Console > Reports > Topic List Parent Map column must show no orphan (blank, GUID-only, or comma-only) entries for topics whose only referring map has been deleted.
- Topics referenced exclusively by the deleted map will have `guidesParentMaps` and `guidesDirectParentMaps` empty or absent after the cleanup.
- Unknown from current evidence: whether cleanup runs synchronously in the AssetDeleteServlet call chain or asynchronously via a post-processing event listener -- this design choice affects test oracle timing and must be confirmed by the implementing engineer.
- Unknown from current evidence: performance impact of the cleanup traversal when a map with thousands of topicrefs is deleted -- no scale benchmark has been established.

**Open Questions**
- Cleanup synchrony: Should the guidesParentMaps/guidesDirectParentMaps cleanup run synchronously within the AssetDeleteServlet request (blocking the delete response) or asynchronously via a post-processing event? QA impact: synchronous means the IT test can assert property state immediately after the DELETE response with no poll; asynchronous means the test must poll with a timeout oracle and a missed-cleanup race is possible if the event fires after the assert window.
- Scale performance threshold: What is the maximum topicrefs count on a single map for EY and Workday? QA impact: if maps exceed ~5,000 topicrefs, the cleanup traversal needs a performance acceptance criterion (max response time or max log latency) to avoid a false pass on small-map tests; without this threshold, a P2 performance scenario cannot have a concrete oracle.
- Config interaction for disable.guidesparentmaps.processing: Should map delete skip cleanup when this config is true (consistent off), or should cleanup always run regardless (cleanup is a correctness concern, not an indexing concern)? QA impact: if cleanup skips when config is off, AC-05 passes only when the property is unchanged; if cleanup always runs, AC-05 must assert cleanup happened despite the config -- the test oracle flips entirely.
- Backfill requirement for existing instances: Do EY and Workday need a one-time job to clean stale GUIDs that accumulated before the fix?
